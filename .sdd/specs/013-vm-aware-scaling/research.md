# VM-aware scaling research

## Findings

- A steady powered-on VM is not reconciled between resyncs (the watcher ignores quick stats, async signalling disables the IP requeue, default resync is 30 minutes), so sampling in status alone would have produced stale data. Found by reading the controller, not by running it; the requeue added for it is untested against a live manager.

- VM Operator had no utilization telemetry: no use of quick stats or the performance manager in `api/`, `pkg/` or `controllers/`. The VM summary, including `quickStats`, is already retrieved on every reconcile.
- The HPA resource-metric path (CPU/memory utilization) relies on Pod metrics and Pods matching the selector, so it cannot serve VMs. That is why spec 012 uses external metrics.
- `external.metrics.k8s.io` can have one provider; KEDA holds it in the lab. A second provider cannot coexist, so a VM-aware adapter uses `custom.metrics.k8s.io`.
- From [replica_calculator.go at v1.35.8](https://github.com/kubernetes/kubernetes/blob/v1.35.8/pkg/controller/podautoscaler/replica_calculator.go): `GetObjectPerPodMetricReplicas` (the `AverageValue` path) uses status replicas and does not list Pods; `GetObjectMetricReplicas` (the `Value` path) calls `getReadyPodsCount` when current replicas are nonzero and the ratio is outside tolerance, and that errors when no Pods match. This was read from a fetched summary of the source and should be re-verified against the exact code before the adapter is built.

## Verification so far

Local: the unit tests above (vcsim status cases; NextUtilization, SummarizeUtilization, ReplicaTotals, UtilizationRequeueDelay; 10 adapter provider specs), the `vmlifecycle`, VM controller and API conversion suites, and `golangci-lint` on the changed packages. `cmd/vm-metrics-adapter/main_test.go` runs the real adapter binary behind an envtest kube-apiserver configured as an aggregator, using the shipped RBAC and APIServices with a CA bundle, and drives it with the HPA's own `k8s.io/metrics` client and real discovery. It found two deployment defects (Service DNS SAN, readiness probe), both fixed.

Live, 2026-10-29, on a dedicated tera-tools Supervisor (Kubernetes 1.35.8+vmware.5; VC `ob-25868994`, ESXi `ob-25869039`, nested, 4 hosts; testbed `db002873-vmhpa-20261029-r2`). VM Operator ran the prototype image (`localhost:5000/vmware/vmop:vmhpa-dc96fdab3`, built from `f41d639cd`) loaded with `hack/deploy-wcp.sh`, with the workload-management capability activated. The adapter ran from `config/vm-metrics-adapter/supervisor` (cert-manager TLS, CA injected into both APIServices, which reported `Available`). VMs were Photon OS 5.0 on `best-effort-small` (2 vCPU) in a vCenter-created namespace. The HPA was `Object`/`AverageValue` on `vm_cpu_usage_mhz`, target 1000 MHz, min 1, max 3, scale-down window 60 s, driven by `hack/workload-scaling/vm_aware.py`.

- Run r1, telemetry and scale-out: the first VM's `status.utilization` appeared within 10 s of power-on, and the adapter served the metric through the aggregator. A burning VM reported about 3,045 then 4,140 MHz. The HPA scaled 1 → 3 (`maxReplicas`) about 2.5 minutes after the first VM powered on, with event "New size: 3". All three replicas burned at about 4,140 MHz each (about 12,400 MHz total), and the HPA held at 3.
- Run r1, scale-in: the burn ended at 11:24:44. The HPA scaled 3 → 1 at 11:28:20 ("All metrics below target"), which is the 60 s stabilization window plus about one 60 s telemetry refresh. Idle VMs report 0 MHz.
- Run r1, outage at minimum: with the adapter scaled to 0, the HPA set `ScalingActive=False` (`FailedGetObjectMetric`) and held 1 replica for 180 s. This only shows that the HPA doesn't scale up without metrics.
- Run r1, recovery failure: after the adapter returned, the HPA stayed `ScalingActive=False` with "no known available metric versions found" for more than 10 minutes. Each control-plane node runs its own kube-apiserver, and the control-plane firewall drops cross-node traffic to ports outside the platform allowlist. The rescheduled adapter Pods left the kube-controller-manager leader's node with no local adapter, so that apiserver could not reach any of them and kept the group `Stale`. The fix in the overlay is one adapter per control-plane node plus `internalTrafficPolicy: Local`. The aggregator reaches the adapter through the ClusterIP, since Supervisor doesn't enable aggregator routing. After the fix, all three apiservers reported the group `Current`, and the HPA recovered within 30 s.
- Run r2, outage during load at max replicas (the strong hold case): the HPA scaled 1 → 3 within about 2 minutes, then the adapter was stopped at 3 replicas. At about 11:51 PDT, the testbed's shared storage failed for reasons outside VM Operator. Two Nimbus VMs were hard-reset at the same moment, with no shutdown record in either: the iSCSI target `iscsi.0`, which booted at 11:52:11, and the infra ESXi host `esx.2`, booted at 11:52:30. No other testbed VM restarted. ESXi `esx.0` logged all paths down on the LUN from about 18:51:06 UTC (APD timeout at 18:53:26). After the reboot the target's disks enumerated in swapped order. Its SCST config names the backing device by kernel name (`filename /dev/sdb`, `nv_cache 1`), so it now exports its own 50 GiB OS disk as LUN 0 in place of the 350 GiB VMFS disk, which is now `/dev/sda` and carries `sharedVmfs-0`'s VMFS. ESXi then reads garbage ("Corrupt heartbeat detected", size 0), and the Supervisor control-plane VMs on that datastore get guest I/O errors and etcd fails. The reason for the reset is not visible from inside these guests; Nimbus pod events were not reachable. The test VMs ran on `esx.0`, `esx.1` and `esx.3`, which did not restart; whether physical-host contention from the CPU burn contributed, for example through HA VM-monitoring resets, is not known. Up to the failure, the replica count stayed at 3. The hold-through-burn-end case is unverified.

Not verified live: the hold past the end of load at max replicas, adapter restart as distinct from scale-to-zero, the telemetry-staleness 503 path (only envtest), multiple ReplicaSets or namespaces, reconcile load from the 60 s requeue, the Kubernetes 1.34 and 1.36 matrix, and a non-nested Supervisor.

## Risks and open questions

- The adapter library adds a direct dependency on `sigs.k8s.io/custom-metrics-apiserver` and `k8s.io/metrics`, about 70 lines of go.mod/go.sum churn, and the binary is about 134 MB.
- The `base/` APIService skips TLS verification; use `secure/` or `supervisor/`.
- On Supervisor the adapter needs host networking, a privileged Pod Security namespace, a node-local image import and one replica per control-plane node, because its port is not in the control plane firewall allowlist. A product integration would need a platform-owned port and image delivery, which is T004a.
- New replicas report a fresh sample with no CPU value while booting. With `AverageValue`, the HPA computes `ceil(total / target)`, so the underestimate only delays scale-out for that VM's share, and the scale-down window absorbs it. It is not extrapolated.
- Nimbus iSCSI targets (Rocky 9, SCST) export the LUN by kernel device name with write-back caching (`nv_cache 1`). Any reset of the target can swap `/dev/sda` and `/dev/sdb` and export the wrong disk, and unflushed writes may be lost. A lab run should check the target's uptime and exported size before trusting the result.

- Status write amplification from sampling is bounded by damping but not measured at scale.
- Samples refresh only on reconcile. The controller now requeues powered-on ReplicaSet VMs every 60 seconds, but the added reconcile load and the resulting freshness have not been measured at scale, and each reconcile's cost is unmeasured; 180 seconds may still be too tight under load.
- Utilization scaling suits stateless, replaceable VMs poorly if they are long-lived or bursty; boot time and quota are not modeled.
- CPU in MHz needs a per-VM target the user must choose; a percentage would need each VM's CPU capacity.
- Whether the aggregate belongs in a ReplicaSet status field instead of the adapter (T007).
